Harness 与 Conversation：API 全景

前四章你已经用过零星几个方法。本章把两个核心接口的全部方法摆到一张地图上， 按用途分组、注明定义位置，让你以后读任何 pi-durable 代码都能对号入座。 这是地图章，不是深潜章 —— commit、task、watch 各自的深处留给后面几章。

学习目标
  • 能按"生命周期 / 会话管理 / 任务 / 提交 / 观察与计量"五组说出 Harness 的方法
  • 能说出 Conversation 的 13 个方法各自的用途
  • 能背出 HarnessOptions 的六个字段及 models/settings 支持函数形式的意义
  • 能区分 Conversation（完整句柄）与 ConversationHandle（任务/工具拿到的受限句柄）

5.1 Harness 接口：五组方法

定义在 src/harness/types.ts:714-756，它还 extends Session（src/types.ts:951），所以 Session 的读写也都在。按用途分组：

  • 生命周期：resume() 启用调度（幂等；关闭后抛错）；close(context)；closed: Promise<SessionEnd>（正常关闭或存储错误后落定，用于监听故障重启）；report(error) 转发非致命错误。
  • 会话管理：root(context, opts?) 取/建根会话；conversation(id, context) 按 ID 取；createConversation({ ownership, agent?, init? }, context) 建独立会话。
  • 任务：getTask(id) 读任务记录；waitForTask(id) 等终态回执；abortTask(id) 打中止标记（返回 marked / terminal）；taskGraph(context) 与 watchTaskGraph(context) 看全库任务图；inspect(context) 活任务与未落定提交的只读快照（不跑任何代码）。
  • 提交：submission(id, context) 重新拿回；abortSubmission(id, context, conversationId?) 撤回（返回 aborted / already_placed / settled / not_found）。
  • 等待与计量：waitForIdle(context) 等所有无主会话空闲；usage(context) 全会话 pi.usage 之和。

从 Session 继承、同样常用的四个：commit(cb, context)（不绑定会话的裸提交线）、 snapshot(token, ...) / documentState(...) / watchDoc(...) （读文档 / 订阅文档，第 6 章）、subscribeCommits(listener)（每个提交后同步回调， 写 UI 同步器时用）。

5.2 Conversation 接口：13 个方法

定义在 src/harness/types.ts:653-709，按你会在代码里用它的顺序排：

  • id — 会话 ID；句柄无状态，比较靠它。
  • agent(context) — 解析后的智能体配置（模型、扩展、工具、sections、cwd），见第 9 章。
  • configure(change, context) — 用一个 AgentChange 原子修改 pi.agent（换模型、加减扩展、改指令、换目录）。
  • submit(submission, context) — 接纳输入或写入（第 10 章展开排队语义）。
  • reset(handoff?, context) — 接纳一条 pi.reset 写入，另起新上下文，可带交接说明。
  • compact(instructions?, context) — 安排手动压缩任务，返回 TaskId<CompactionResult>（第 10 章）。
  • commit(cb, context) — 绑定此会话的提交（tx.createTask() 默认归属它），第 6 章。
  • context(context, { at? }) — 读激活上下文：head 标记、原始条目、各条目贡献的模型消息、拼好的下轮 messages。at 可看历史某点的上下文（fork 会从那里开始的样子）。
  • entries(query, limit, cursor, context) — 翻分叉感知的会话历史（默认新在前）。
  • fork(at, options, context) — 从某条可见条目分叉出独立会话。
  • abort(context, opts?) — 撤回排队输入、中止其普通所有权范围内的活任务、等到空闲；{ background: true } 连后台工作一起。
  • waitForIdle(context) — 等普通所有权范围没有存活的前台任务。
  • viewState(context) / watch(context) — 结构化视图与逐帧观察（第 10 章）。

5.3 HarnessOptions：六个旋钮

const harness = await Harness.open(storage, {
	models,            // 必填：Models 对象，或 () => Models（每次使用时求值）
	registry,          // 必填：RegistryReader（createRegistry() 的返回值）
	settings,          // 可选：运行策略对象，或 () => settings（getter 实现动态配置）
	env,               // 可选：(target, context) => ExecutionEnv，为每次工具调用/渲染建环境
	conversationCreated, // 可选：每个建会话的 commit 里跑一次（给会话塞你的文档）
	now,               // 可选：时钟注入（测试里固定时间）
	onReport,          // 可选：接收不致命的错误（抛错的 hook、监听器等）
}, context);

两个值得强调的设计：

  • models 和 settings 都接受函数 （src/harness/types.ts:587-594）：每次使用时重新求值。配合 getter， 可以做到改一个配置对象就全局生效，不用重开 Harness。README 的 Settings 一节给的范例就是 get followUpMode() { return userSettings.followUpMode; } —— 设置对象在跑动中变化， 下一次边界就按新值排。
  • conversationCreated 是给每类会话注入你文档的钩子： 它在每个创建/分叉会话的 commit 里运行（包括工具裸调 tx.createConversation()）， 你在这里 tx.doc(YourDoc, record.id)，保证任何途径诞生的会话都带上你的状态。

settings（HarnessSettings，types.ts:539-560）里的字段先混个眼熟，用到再回查：extensions（默认扩展选择）、stream（请求参数）、retry、compaction（压缩阈值）、progress（进度提交节奏）、toolExecution（parallel/sequential）、steeringMode/followUpMode、contextRetentionMs/documentRetentionMs（内存驻留时长）。

5.4 ConversationHandle：任务与工具眼中的会话

在工具或任务的 execute() 里，你通过 api.conversation(id, context) 拿到的是 ConversationHandle（src/harness/types.ts:127-134）而不是完整的 Conversation —— 只有 submit、abort、waitForIdle 三个操作。 这是刻意的：句柄绑定到当前调用（invocation），调用结束（工具返回、任务中止、 Harness 关闭）后它的所有操作都会拒绝 —— 但已经接纳的提交仍然是持久的，不会跟着消失。 第 7 章的子代理示例会用到它。

5.5 本章回顾

  • Harness 五组：生命周期 / 会话 / 任务 / 提交 / 等待与计量，外加 Session 继承的读写。
  • Conversation 13 法：配置、喂入、原子写、读史、分叉、停等、观察。
  • HarnessOptions 六旋钮；models/settings 可传函数实现免重开的动态配置。
  • conversationCreated 保证任何途径新建的会话都带你的文档。
  • 工具/任务内部拿的是受限的 ConversationHandle，随调用结束失效。
常见坑
  • 把 conversation.context() 与 CONTEXT（取消令牌）混淆 —— 前者是读模型上下文的方法，后者是每个调用的最后一个参数。
  • 关闭后再 resume() —— 抛错；resume 只在存活期内幂等。
  • 在宿主代码里寻找完整的 ConversationHandle 行为 —— 它故意只有三个方法，别指望 configure。
  • 忽略 closed promise —— 生产服务应监听它实现故障后重开（第 10 章错误模型）。
