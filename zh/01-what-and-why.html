认识 pi-durable：它解决什么问题

你不需要先懂 pi 的其他部分。这一章只回答三个问题：pi 是什么、 一个 AI 智能体（agent）在长时间运行时为什么会"崩坏"、pi-durable 用什么思路解决它。 读完你就知道这个包在整个系统里的位置，以及它为什么被设计成后面九章的样子。

学习目标
  • 能说出 pi 仓库里各包的大致分工，以及 pi-durable 在其中的位置
  • 能用自己的话讲清"长时智能体 + 进程随时会死"这对矛盾，并给出一个具体翻车场景
  • 能复述 pi-durable 的核心承诺：先提交、后展示（committed before shown），以及"一切修改都走原子提交"
  • 能画出 pi-durable 的分层：宿主程序 → Harness → Session/Storage，以及它依赖的 pi-ai 与 chord

1.1 pi 是什么

你正在看的仓库 /Users/jack/Documents/pi 是 pi —— 一个用 TypeScript 写的 AI 编程智能体（coding agent）及其配套设施的 monorepo。它不是一个单一的程序，而是一组 npm 包，各自负责一层：

  • @earendil-works/pi-ai（packages/ai）— 模型访问层：统一各家大模型（OpenAI 等）的请求、流式返回、工具调用协议。
  • @earendil-works/pi-agent（packages/agent）— 智能体循环的纯逻辑层。
  • @earendil-works/pi-tui（packages/tui）— 终端界面库。
  • @earendil-works/pi-coding-agent（packages/coding-agent）— 最终那个终端编程助手，把上面的层组装成产品。
  • @earendil-works/pi-durable（packages/durable）— 本书的主角。官方一句话介绍（见 packages/durable/package.json）："Durable conversation, task, and document runtime for Pi" —— 面向 Pi 的、可持久化的会话 / 任务 / 文档运行时。

注意 README 顶部的标注：Experimental（实验性），API 会在版本间无预警地变动。 本书的一切结论都以你本地这份源码为准（版本 1.3.0），引用时给出真实文件路径与行号， 例如 packages/durable/src/harness/harness.ts:460。

1.2 问题：智能体是"长任务"，而进程随时会死

一个编程智能体的一次工作循环通常长这样：用户发消息 → 调模型 → 模型要求执行工具 （读文件、跑 bash、改代码）→ 把工具结果喂回模型 → 可能再来几轮 → 最终回答。 这个循环可能跑几十分钟，中间夹杂网络请求、子进程、大文件读写。

具体翻车场景：假设模型刚决定执行 bash: npm test，测试要跑 8 分钟。 第 4 分钟时你的笔记本合盖了、SSH 断了、或者进程被 kill。重新打开后会发生什么？ 在一个把会话放在内存里的朴素实现里：

  • 模型的回复丢了 —— 它还没写进任何地方，用户要重新问一遍（模型费白花）。
  • 更糟：如果你做过"边生成边写文件"的持久化，文件里可能有半条模型消息 —— 存储和真实进度对不上。
  • 测试进程成了孤儿，重启后没人知道它跑没跑完、结果有没有被消费。
  • 最糟：如果重启后重放整个对话，npm test 这种有副作用的操作会被再执行一次。

这类系统的术语叫 durable execution（持久化执行）：把"正在做什么"的每一步 都先写进可靠存储，进程死了也能从断点继续，而且不重复已完成的副作用。 pi-durable 就是给 Pi 系列提供这套能力的包。

1.3 pi-durable 的三个核心设计决定

README 的第一段就是全部设计的浓缩（packages/durable/README.md:5）：

Conversations, model turns, tool calls, and your own state are committed to storage before anything is shown. If the process dies mid-turn, reopening the storage picks the work up where it stopped.

拆成三个可检验的决定：

  • 决定一：唯一写入口 —— 原子提交（commit）。 会话里的任何修改（追加一条消息、改一个文档、创建一个任务）都不能单独发生， 必须打包在一次 commit() 里，要么全部落盘、要么全部没有发生。 这是你在问题里提到的 commit —— 它不是 git 的 commit，而是这个包自己的一等概念， 第 2 章和第 6 章会专门拆开讲。
  • 决定二：任务即状态机（task）。 每件耗时的事（调模型、执行一个工具、做一次摘要）都是一个 任务， 它在每一步之前把"下一步从哪继续"的检查点（checkpoint）写进存储。 进程重启后，调度器看到 pending 的任务，从上一个检查点继续，而不是从头重放。 每个任务都有唯一的所有者（owner）—— 它所在的会话，或另一个任务 —— 这让"中止"能像树一样级联。
  • 决定三：UI 只读已提交状态。 界面看到的一切（流式回答的半截文本、工具输出）都是已提交的存储状态的投影， 通过订阅（watch）拿到。没有任何"只存在于内存里的显示状态"， 所以晚加入的观察者、崩溃后的重连，看到的都是一致的画面。

1.4 分层：pi-durable 站在哪里

pi-durable 不自己连模型、也不自己发明 JSON 状态管理。它依赖两个邻居 （见 packages/durable/package.json:145-152 的 dependencies）：

  • @earendil-works/pi-ai — 所有模型请求走它。pi-durable 不认识 OpenAI 或 Anthropic，它只拿着一个 Models 目录对象。
  • @earendil-works/chord — 文档状态框架：类型化 JSON 文档、增量（delta）操作、可订阅状态、以及贯穿全库的 Context（取消令牌）。

另一个会出现的名字是 Chord Context：pi-durable 里 每一个异步调用的最后一个参数都是它，它携带取消信号。 BACKGROUND_CONTEXT 是"永不取消"的那个。取消一个 wait() 只取消这次等待， 永远不会取消已被持久化接纳（admitted）的工作 —— 这个区别后面会反复出现。

目录结构也印证这个分层（packages/durable/src/）： session/ 是提交线与会话内核（第 6 章）， harness/ 是智能体机械（第 5、7、9、10 章）， storage/ 是四个后端（第 4 章）， tools/、env/、images/ 是内置工具与执行环境（第 8 章）， codemode/、tool-search/ 是可选扩展（第 9 章）。

1.5 本章回顾

  • pi 是一个 monorepo；pi-durable 是其中提供"持久化会话 / 任务 / 文档运行时"的实验性包（1.3.0）。
  • 长时智能体 + 进程随时会死 = 需要持久化执行：断点续跑、不重放副作用、存储与展示永远一致。
  • 三个核心设计：唯一写入口（原子 commit）、任务即带检查点的状态机、UI 只读已提交状态。
  • 每个异步 API 都吃一个 Chord Context（取消令牌）；取消等待 ≠ 取消工作。
  • 依赖：pi-ai（模型）、chord（文档/取消）；自己提供四种 Storage 后端。
常见误解
  • 把 commit 当成 git commit。这里是"一次原子存储写入"的运行时概念，与版本控制无关。
  • 以为 pi-durable 会自动连模型。模型目录（Models）由你通过 pi-ai 构建后传入，它只是使用。
  • 以为持久化 = 定期保存。这里是"任何东西展示之前其提交必须已落盘"，顺序是设计出来的，不是定时刷盘。
  • 以为它稳定。README 明说 Experimental：API 会在版本间无预警变化。
