第 4 章 · 持久化

持久化与恢复：换掉 MemoryStorage，进程死了也能续

第 3 章的程序一退出就什么都没了，因为用的是 MemoryStorage。本章换上真正的后端， 讲清崩溃后重开时到底发生什么、怎么保证不重复提交、以及四个后端各自的取舍。

学习目标
  • 能写出 SQLite 版的最小"重开续跑"程序（open → root → resume）
  • 能说明 resume() 做什么、哪些调用会隐式启动调度器
  • 能用 requestId 与 harness.submission(id) 写出崩溃安全的提交重试
  • 能按场景选后端：Memory / SQLite / JSONL / Cloudflare Durable Object，并说出各自的关键限制
  • 能解释 pi.provider 里的持久 sessionId 为什么能保温提供商 prompt 缓存

4.1 四个后端一张表

README 的存储表格（README.md:664-669）浓缩如下：

  • Memory — MemoryStorage（包根导出）。什么都不持久化，测试与教学用。
  • SQLite — openNodeSqliteStorage(file)（@earendil-works/pi-durable/storage/sqlite/node）。一个数据库文件；WAL 模式 + synchronous = NORMAL：提交能扛住进程崩溃；断电/宿主机故障可能丢最新一条。长跑智能体的默认选择。
  • JSONL — openNodeJsonlStorage(directory, context)（/storage/jsonl/node）。一个目录里的追加式文件；{ fsync: true } 可在每条提交标记前刷盘。整个历史也留在内存里，内存随历史增长 —— 适合短期任务，长跑用 SQLite。
  • Cloudflare Durable Object — openDurableObjectSqliteStorage(ctx.storage)（/storage/sqlite/cloudflare）。一个 SQLite 型 Durable Object 的存储；提交即其存储事务。

两条全局规则（README.md:677 与 spec §10）：

  • 一个进程独占一个存储：没有跨进程锁。两个进程同时打开同一 SQLite 文件是不受支持的用法。
  • 可移植内核（/storage/sqlite、/storage/jsonl）不依赖 Node API —— 给它们一个异步 SqliteDatabase 门面或 env 包里的 FileSystem，就能在 Bun、Cloudflare 上跑。

4.2 重开与 resume()：断点在哪

把第 3 章的程序换成 SQLite，就得到跨进程版本（README.md:107-113）：

import { openNodeSqliteStorage } from "@earendil-works/pi-durable/storage/sqlite/node";

const harness = await Harness.open(
	await openNodeSqliteStorage("./session.sqlite"),
	{ models, registry },
	context,
);
const root = await harness.root(context); // 和上次是同一个根会话
harness.resume();                          // 继续上个进程没做完的 run

重开时发生的两件事：

  1. 对账：打开存储时把幸存的 running 任务改回 pending（src/harness/harness.ts:252-255 的 openTasks）。因为"running"只表示被某个存活进程的调用占用，那个进程死了，任务自然回到可调度状态，并带着它最后的检查点。
  2. 调度：resume() 启动任务调度器。不调也行 —— 任何"要进度"的调用都会隐式启动它：submit()、compact()、abort()、Submission.wait()、waitForTask()、两个 waitForIdle()（src/harness/types.ts:715-719）。只读的观看者永远不会启动调度 —— 一个纯 UI 进程可以打开存储看而不干活。

4.3 崩溃安全的提交：requestId 幂等

场景：你的服务收到用户消息，调 submit()，网络超时了。客户端重试 —— 会不会问两遍？ 不会，只要带同一个 requestId（README.md:117-126）： 

const s1 = await root.submit(
	{ type: "input", content: "Hello", requestId: "greeting-1" }, context);
// 进程重启后，用同一个 requestId 再提交：
const again = await root.submit(
	{ type: "input", content: "Hello", requestId: "greeting-1" }, context);
// again.id === s1.id —— 拿回的是同一个 submission，而不是新的

去重是会话范围内的（SubmissionRecord.requestId 的注释： "Host-provided deduplication key, scoped to the conversation"，src/types.ts:376）。 如果重启后你手里有上次的 submission ID，也可以直接 harness.submission(id, context) 重新拿回等待句柄 —— 这就是"重开进程后接着等答案"的完整写法。

4.4 pi.provider：不变的会话身份

每个会话在 pi.provider 文档里持有一个 UUIDv7。它被转发给 pi-ai 作为 sessionId，提供商拿它做 prompt 缓存与会话亲和。关键性质：重开、重试、 reset、压缩、换模型都不换身份；子会话与分叉拿全新身份。 这解释了一个反直觉的好性质：哪怕经历了上下文压缩，提供商仍然认得这是同一个会话， 缓存命中率不因为内部操作而清零。

4.5 与宿主共享数据库：前缀与适配器

两个进阶点，用到再查即可：

  • 表前缀：三个 SQLite 入口都收 { prefix: "pi_" }，把表和索引圈进自己的命名空间，可与宿主表共库。前缀须是合法 SQLite 标识符、不能以 sqlite_ 开头；改前缀不做数据迁移。
  • Cloudflare 共库：同一 storage 对象打开的多个 Pi 存储自动共享操作队列；宿主自己的表查询要走同一个适配器（DurableObjectSqliteDatabase），绕开队列直连存储可能被 Pi 的事务回滚。

自定义后端有官方一致性测试套件：registerStorageConformance() （@earendil-works/pi-durable/testing），任何 Vitest/Jest 兼容的 runner 都能跑。 适配器契约（README.md:690-697）：promise 风格的 exec / run / get / all / transaction / close，事务回调里只能用传入的事务句柄。

4.6 本章回顾

  • SQLite 是长跑默认：WAL + NORMAL，扛进程崩溃，断电可能丢最新一条；JSONL 简单但内存随历史涨；Memory 不持久；DO 面向 Cloudflare。
  • 重开 = 对账（running→pending，带着检查点）+ 可选 resume()；只读观察者不触发调度。
  • 同 requestId 重试拿回同一 submission（会话内去重）；harness.submission(id) 重获等待句柄。
  • pi.provider 的 UUIDv7 跨一切内部操作稳定，保住提供商缓存亲和；分叉/子会话另起身份。
  • 一库一进程；共享库用前缀或统一适配器；自定义后端跑 conformance 套件。
常见坑
  • 两个进程开同一个 SQLite 文件 —— 没有跨进程锁，行为未定义。
  • 期待断电级持久 —— 默认配置承诺的是进程崩溃级；要更强需 JSONL + fsync 或调存储配置。
  • 重试 submit 不带 requestId —— 会真的提交两次。
  • 以为 resume() 必须显式调用 —— 大多数"要进度"的调用都会启动调度器；反之纯观看进程不会误启动。
  • 长跑服务用 JSONL —— 历史全驻内存，越跑越胖，换 SQLite。
