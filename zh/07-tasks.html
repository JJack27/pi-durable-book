Task：持久状态机与所有权树

任务是 pi-durable 里"能干活的最小持久单位"。回答模型、执行工具、压缩摘要这些内置行为 全部是任务 —— 学会任务，你就看穿了这台机器的心脏。本章覆盖：任务定义的解剖、 五种状态与五种结局、检查点纪律（不提交进度 = 故障）、等待与子任务、中止的级联， 以及子代理这个最重要的应用模式。

学习目标
  • 能用 defineTask 写出多阶段任务，并解释 initial / phases / abort / migrate 各自的职责
  • 能背出 TaskState 五态与 TaskOutcome 五种结局的含义
  • 能说清检查点纪律：阶段处理器必须提交新状态，否则任务 faulted
  • 能用 waiting + on + policy（failFast / allSettled）编排子任务
  • 能解释所有权树上的中止级联与 background / abandonOnRestart 两个逃生门
  • 能读懂 README 的子代理工具模式并复述它为什么 replay: safe

7.1 任务定义的解剖

import { defineTask } from "@earendil-works/pi-durable"; // src/tasks.ts:4

const Payment = defineTask<
	{ card: string },                      // I：输入（不可变，任务存活期间一直带着）
	{ phase: "charge" } | { phase: "capture"; txId: string } | { phase: "done" },  // S：检查点
	{ receiptId: string },                 // R：成功结果
	{ onCharge?: (txId: string) => void } // H：可选 hooks（第 9 章）
>({
	name: "app.payment",       // 注册表里的种类名，存进 TaskRecord.kind
	version: 1,                // 定义版本，配合 migrate 做在线升级
	initial: (input) => ({ phase: "charge" }),        // 新任务的第一个检查点
	phases: {                  // 相位映射：按 checkpoint.phase 精确分发
		charge:  async (task, runtime, context) => { /* ... */ },
		capture: async (task, runtime, context) => { /* ... */ },
		done:    async (task, runtime, context) => { /* ... */ },
	},
	abort: async (task, runtime, context) => { /* 中止协议：清理外部效果，必须提交终态 */ },
	migrate: (input, checkpoint, fromVersion) => ({ input, checkpoint }), // 可选
});

记住一句话：检查点 S 里必须装下"从哪里继续"的全部信息。 capture 相位带着 txId，因为重启后从这里继续时，需要知道之前扣款的事务号。

7.2 状态与结局

TaskState（src/types.ts:503-537）五态：

  • pending — 可调度，带完整检查点。
  • running — 被某个存活进程的调用占用（重启对账后回 pending）。
  • waiting — 停车场：等 on 列表里的任务全部终态；期间不跑任何代码。
  • completing — 结局已定，但等它拥有的普通工作排空才转 terminal（见 7.4）。
  • terminal — 永久回执。

TaskOutcome（src/types.ts:466-500）五种结局，注意它们的语义分工：

  • completed — 成功，带 result。
  • failed — 业务失败：任务代码自己提交的、预期内的失败（比如卡被拒），带 error: { message, detail? }。
  • aborted — 被显式中止，走的是任务的 abort 协议，可带 reason。
  • orphaned — 定义失踪：注册表里找不到能接手的定义（或迁移失败），只能坐以待毙地标孤儿。
  • faulted — 契约违约：阶段处理器抛了未捕获异常，或跑完却没提交任何持久进展。

failed 与 faulted 的区别是面试级考点：failed 是你声明的设计内失败，faulted 是运行时抓到的你违约。

7.3 检查点纪律：阶段处理器怎么写

一个阶段处理器的铁律（src/types.ts:148-155 的 PhaseHandler 文档注释）：

It must commit a changed checkpoint or a terminal outcome through runtime.commit(); returning without durable progress faults the task.

也就是说，每个阶段的结尾只有两条合法出路：

charge: async (task, runtime, context) => {
	const txId = await chargeCard(task.input.card, context);      // 外部副作用
	await runtime.commit(async (tx, current) => {
		// 出路一：提交新检查点（返回 NextTaskState，同一提交里替换任务状态）
		return { status: "running", checkpoint: { phase: "capture", txId } };
	}, context);
},
capture: async (task, runtime, context) => {
	const receiptId = await capture(task.state.checkpoint.txId, context);
	await runtime.commit(async (tx) => {
		// 出路二：提交终局
		return { status: "terminal", outcome: { status: "completed", result: { receiptId } } };
	}, context);
},

关键顺序：先做外部副作用，再提交检查点。若反过来（先提交"已扣款"再扣）， 崩溃会留下说了谎的检查点。若只做副作用不提交 —— 返回即 faulted，这是运行时逼你诚实。 这就是 spec 5.2 节所称的 effect sandwich（效果三明治）：副作用夹在两个提交之间， 前一个提交声明"我要做了"（意图），后一个提交记录"做成了什么"。

runtime 还提供一套趁手工具（src/types.ts:170-241）： signal（中止信号，长操作要观察它）、memo(name, candidate) （首写胜出的持久便签 —— 生成任务用它存"这次请求 ID"，崩溃重跑不会重复生成）、 sleep(until)、outcomes(ids)（批量取终态）、 conversation(id)（拿受限句柄操纵子会话）、report(error)、 hooks（跑扩展钩子，第 9 章）。

7.4 等待子任务：waiting 与 completing

README 的结账示例（README.md:590-606）展示了标准编排骨架：

pay: async (task, runtime, context) => {
	await runtime.commit(async (tx) => {
		const payments = [];
		for (const card of task.input.cards) {
			payments.push(
				await tx.createTask(Payment, { card },
					{ ownership: { kind: "task", taskId: task.id } }),  // 子任务归我
			);
		}
		// 全部完成后在 decide 相位恢复；第一个失败则中止其余
		return {
			status: "waiting",
			checkpoint: { phase: "decide", payments },
			on: payments,
			policy: "failFast",
		};
	}, context);
},
decide: async (task, runtime, context) => {
	const outcomes = await runtime.outcomes(task.state.checkpoint.payments, context);
	// ...提交本任务自己的结局
},
  • waiting 期间不跑代码：进程可以死、可以关，恢复完全由存储状态驱动。on 里还可以放别人的任务（仅 allSettled 时）。
  • 两种 policy：allSettled 等全部终态；failFast 第一个失败即刻中止其余。
  • completing 的意义：任务想结束（比如 aborted）时，它拥有的普通工作还在飞。结局先挂起（completing），等下属全部终态才转 terminal —— waitForTask() 这时才返回。failed/aborted 的结局会先中止下属再进入 completing，所以"中止自下而上"：每个任务先撤干净自己管的，再轮到自己的 abort 处理器收尾。

7.5 TaskOptions：归属与两个逃生门

await tx.createTask(Payment, input, {
	ownership: { kind: "conversation" },  // 必填：会话拥有（顶层）或 { kind: "task", taskId }（子任务）
	conversationId: otherConversationId,  // 可选：归属别的会话（默认 tx 绑定的会话）
	background: true,                     // 仅会话拥有：排除在普通空闲等待/会话中止/级联之外
	abandonOnRestart: true,               // 创建者只在内存里等它：重启后直接按 restart 理由中止
});
  • background 是所有权边界：后台子树在父会话 Esc（abort）时幸存，也不拖住父的空闲判断；要连它一起停用 abort(context, { background: true })。
  • abandonOnRestart 诚实面对"没人会回来等它"的任务：下个 Harness 开始调度时发现它还活着，先打上 abortReason: "restart" 的中止标记再谈别的。不可重放的工具（第 8 章）的嵌套调用与子任务自动获得这个待遇。

7.6 子代理：任务拥有会话

所有权不止"任务拥有任务"—— 会话也能被任务拥有 （ConversationOwnership = { kind: "ownerless" } | { kind: "task", taskId }， src/types.ts:300）。这就是子代理模式的骨架（README 的示例，README.md:547-573）： 

const subagent = defineTool({
	name: "subagent",
	parameters: Type.Object({ task: Type.String() }),
	replay: "safe",                       // 崩溃重跑时找回同一个孩子，而不是再开一个
	execute: async (args, api, context) => {
		const child = await api.commit(async (tx) => {
			// 所有权索引记住了孩子：重跑按 ownerTaskId 找回
			const existing = (await tx.scanConversations({ ownerTaskId: api.taskId }, 1)).items[0];
			if (existing !== undefined) return existing.id;
			const created = await tx.createConversation({
				ownership: { kind: "task", taskId: api.taskId },  // 孩子归本调用
			});
			await configure(tx, created.id, { model: cheap, extensions: { remove: [Subagent] } });
			return created.id;
		}, context);
		await api.details({ conversationId: child }, context);   // 让 UI 能挂到孩子上
		const request = { type: "input", content: args.task,
			requestId: `subagent:${api.taskId}` } as const;
		const handle = await api.conversation(child, context);
		const settled = await (await handle!.submit(request, context)).wait(context);
		return { output: [{ type: "text", text: settled.status }] };
	},
});

被任务拥有的会话服从三件事：调用中止/失败 → 孩子跟着中止；父空闲要等孩子空闲；background: true 的锚任务可以隔断这层父子（持久子代理的标准做法，见 test/examples/23-subagent-background.ts）。

7.7 看见任务：taskGraph 与 inspect

  • harness.taskGraph(context) / watchTaskGraph(context) — 全库活任务的一张图（每个节点带 owner 边、状态、是否 background/被标记中止、拥有的会话），任务面板与调试用。任务随创建它的提交出现、随使它 terminal 的提交消失。
  • harness.inspect(context) — 只读快照，多一个 taskGraph 不给的信息：pending 任务是否因定义缺失而 blocked（missing_task / task_too_old / migration_failed）。
  • 三个内置任务（src/harness/registry.ts 的 BUILTIN_TASKS）：pi.generation（generation.ts:118，v1）、pi.tool（tool.ts:120，v2）、pi.compaction（compaction.ts:112，v1）。

7.8 本章回顾

  • defineTask 四要素：initial 检查点、按 phase 分发的处理器、abort 协议、migrate 版本迁移。
  • 五态 pending/running/waiting/completing/terminal；五结局 completed/failed/aborted/orphaned/faulted；failed≠faulted。
  • 铁律：副作用后必须 runtime.commit 新检查点或终局，否则 faulted（effect sandwich）。
  • waiting = 零代码停车等 on 列表；failFast 第一个失败中止其余；completing 等下属排空；中止自下而上。
  • ownership 三形态：会话拥有（可 background）、任务拥有、任务拥有会话（子代理）。
  • taskGraph 看图，inspect 看 blocked；内置 pi.generation / pi.tool / pi.compaction。
常见坑
  • 阶段处理器只做副作用不 commit —— 返回即 faulted，白干。
  • 先 commit 检查点再做副作用 —— 崩溃后检查点说谎，重跑跳过未发生的副作用（或重复执行）。
  • 把外部错误直接 throw 出去想要 failed —— throw 出去是 faulted；业务失败应当自己 commit failed 结局。
  • 在 waiting 状态里幻想还有代码在跑 —— 没有；一切恢复靠调度器看存储。
  • 改了任务检查点结构但不升 version / 不写 migrate —— 老任务 orphans/blocked，新代码接不上。
  • 期待 abortTask 立即生效 —— 它先标记并自下而上停下属，等轮到该任务自己的 abort 处理器，才变 terminal。
