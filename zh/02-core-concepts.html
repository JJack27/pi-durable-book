核心概念：Harness、Conversation、Entry、Commit、Document、Task、Submission

pi-durable 的 API 读起来费劲，八成是因为这七个名词。本章把它们一次讲透 —— 每个词是什么、 不是什么、放在哪一层。之后所有章节都建立在这套词汇上。你问的"commit 到底是个什么东西"， 答案就在 2.4 节。

学习目标
  • 能不看资料说出七个核心名词各自的定义与所属层次
  • 能解释 Entry 的双通道结构（model 消息 vs data 数据）和 head 的作用
  • 能准确描述 commit 的原子性保证，以及"一次 commit 里能同时做哪三类事"
  • 能读懂 README 里那段"一次输入对应的 entries 与 tasks"轨迹图
  • 能列出五个内置文档（pi.agent / pi.provider / pi.live / pi.inbox / pi.usage）各自的用途

2.1 Harness：一个打开的存储 + 智能体机械

Harness（src/harness/harness.ts:181，class HarnessImpl） 是你拿到手的根对象：一份打开的存储（Session），加上在它上面跑智能体的全部机械 —— 任务调度器、提交（submission）管理、视图（view）、注册表（registry）引用。 README 的措辞是："one open storage plus the machinery that runs agents on it"。 关键性质：

  • 所有变更都汇进同一条原子提交线（mutation line），由底层 Session 串行化；
  • Harness 是有生命周期的：Harness.open() 创建，close() 或一次存储错误终结；
  • 它自己几乎不存状态在内存里 —— 机器读的、UI 看的，都来自存储。

2.2 Conversation：一份 transcripts（会话记录）

Conversation（会话）就是一个不可变条目的序列 —— 一份对话记录。 注意三点，都是从 src/harness/types.ts:653 的接口注释里来的：

  • 句柄无状态。你拿到的 Conversation 对象只是个把手，比较两个会话要用 id，不是 ===。
  • root 会话：每个存储有一个保留的根会话，harness.root() 第一次调用时创建它，ID 恒为 ROOT_CONVERSATION_ID = 1（src/types.ts:39）。跨进程重开存储，root() 拿到的还是同一个会话。
  • 还可以创建独立会话（createConversation()）和分叉（fork(entryId)，从某条历史条目开始另起炉灶）。

2.3 Entry：一条不可变的记录，双通道

Entry（条目）是会话里的最小记录单位，定义在 src/types.ts:334 （EntryRecord）。一条条目一经提交就永不修改 —— 想改历史，只能追加新条目去覆盖。 它有两个互不干扰的通道：

  • model：这条条目贡献给模型上下文的消息（比如一条 user 消息或 assistant 消息）。没有 model 的条目，模型根本看不见 —— 纯粹是给你的 UI 或记账用的。
  • data：给应用层的 JSON 载荷（例如聊天消息的作者、头像这类 UI 数据）。

其余字段：kind（种类标签）、head（激活上下文的起点标记，见下）、edits（对更早条目模型消息的省略/替换）、byTaskId（哪个任务写的）。

内置的六种条目定义在 src/entries.ts:15-34，全部以 pi. 开头：

  • pi.user — 用户输入（model 是一条 UserMessage）。由 submission 写入。
  • pi.assistant — 模型的一次回复（一条 AssistantMessage，可能带工具调用）。由 generation 任务写入。
  • pi.system — 系统提示词/工具变化的位置标记：模型看到的系统提示词变化被存成这种条目，只有变化的部分才重发，用来保温提供商的 prompt 缓存。
  • pi.tool-result — 工具结果（一条 ToolResultMessage + data.diagnostics）。由工具任务写入。
  • pi.reset — 重置：新上下文的起点，head: "self"。老条目留在存储里，但模型不再看见。
  • pi.compaction — 压缩摘要：把旧上下文总结成一条，head 指向保留的第一条条目。

head 是什么？模型看到的"激活上下文"不是全部历史，而是从最新的 head 标记开始 到尾部的那段。pi.reset 和 pi.compaction 都会立起一个新的 head， 于是更早的条目自动退出模型视野（但仍在存储里，供你翻旧账）。 自定义条目种类不能以 pi. 开头 —— 这是保留前缀。

2.4 Commit：一次原子写入（你问的那个 commit）

Commit 不是 git 概念。它是 pi-durable 自己的一等公民： 一次要么全有、要么全无的存储写入。README 的定义原文： "an atomic write. conversation.commit((tx) => ...) can append entries, edit documents, and create tasks together; either all of it is stored or none of it is."

用法形态是一个事务回调：

const result = await conversation.commit(async (tx) => {
	const entry = await tx.appendEntry(conversation.id, { kind: "app.note", data: { text: "hi" } });
	const todos = await tx.doc(Todos, conversation.id);
	todos.items.push("写一条笔记");
	await tx.createTask(MyTask, input, { ownership: { kind: "conversation" } });
	return entry.id; // 回调的返回值就是 commit() 的返回值
}, context);

一次 commit 里可以同时做三类事，并且作为整体落盘：

  • 追加条目（tx.appendEntry）— 改对话记录；
  • 编辑文档（tx.doc(...) 返回可变的 Draft，改完自动算增量）— 改结构化状态；
  • 创建任务 / 提交记录（tx.createTask、tx.createSubmission 等）— 安排工作。

原子性的两个推论，后面章节会反复用到： 回调抛异常则整个回滚，一条都不会写入； 观察者（watch）看到的永远是完整的提交，不存在"半个提交"的中间态。 commit 落盘后拿到一个严格递增的序号 Seq（src/types.ts:36）， 整个存储的历史就是 Seq 的序列。第 6 章把 Tx 的每个方法拆开讲。

2.5 Document：住在会话旁边的类型化 JSON 状态

Document（文档）是与会话记录并存的结构化状态：一个带类型、带版本号的 JSON 对象， 用 defineDoc() 声明（第 6 章详讲），只能在 commit 里改。 它和条目的分工是：条目是"发生过什么"的日志，文档是"现在是什么样"的快照。

五个内置文档（都在 commit 里被 Harness 自己维护）：

  • pi.agent — 这个会话用什么跑：模型、思考等级、扩展、工具、指令、工作目录（src/harness/agent.ts:43）。
  • pi.provider — 面向提供商的会话身份（一个持久化的 UUIDv7），重开、重试、重置、压缩、换模型都不变；转发给 pi-ai 当 sessionId，用来命中提供商的 prompt 缓存。
  • pi.live — 正在发生什么：流式中的回答、重试、每个工具调用的输出与详情。UI 的"实时感"全来自它。
  • pi.inbox — 排队中的提交：会话忙时新输入在这里排队（第 10 章）。
  • pi.usage — 花了多少钱：按 provider/model 和按工具名累计的 token 与费用。

2.6 Task：带检查点的状态机，人人都有 owner

Task（任务）是一件持久化的工作，本质是个状态机： 它的定义是一组阶段（phase）处理器，每走一步之前先把"检查点"（下一步从哪继续的全部状态）提交进存储。 进程死了，任务回到 pending；下次调度时从检查点继续。src/types.ts:244 的 TaskDefinition 是完整形状（第 7 章细讲）。

最重要的规则：每个任务都有唯一所有者（owner） —— 要么是它所在的会话（顶层任务）， 要么是同会话里的另一个任务（子任务）。所有权构成一棵树，"中止"沿树级联： 中止一个任务会先中止它拥有的一切。pi-durable 自己的回答、工具执行、摘要压缩都是内置任务： pi.generation（调模型）、pi.tool（执行一次工具调用）、pi.compaction（做摘要）。

2.7 Submission 与 turn / run

Submission（提交记录）是你交给会话的一样东西：要么是用户输入 （input，会触发一轮模型工作），要么是被动写入（write，只追加条目、不打扰模型）。 submit() 返回的对象可以 wait()（等到 done / unanswered）、abort()（撤回还在排队的）。 它是持久化的 —— 重启后还能用 harness.submission(id) 重新拿回来。

最后两个小词：

  • turn（轮）：模型的一次回复加上它的工具调用；
  • run（运行）：从一条输入到它最终回答之间的所有轮。会话在 run 进行中就是"忙"（busy）。

2.9 本章回顾

  • Harness = 打开的存储 + 智能体机械；Conversation = 不可变条目序列；句柄无状态，按 id 比较。
  • Entry 双通道：model 给模型、data 给应用；head 标记激活上下文起点。
  • Commit = 一次原子写入：条目 + 文档 + 任务打包落盘，回调抛异常则全回滚；落盘得 Seq。
  • Document = 类型化 JSON 状态，只能在 commit 里改；内置五个：pi.agent / pi.provider / pi.live / pi.inbox / pi.usage。
  • Task = 带检查点的状态机，必有 owner；内置 pi.generation / pi.tool / pi.compaction。
  • Submission = 被持久接纳的输入或写入，可 wait / abort / 重启后找回；turn 是一轮，run 是一整个回答过程。
常见误区
  • "改一条旧消息"。条目不可变；正确做法是追加新条目（或用 edits 在上下文层面省略/替换旧消息的贡献）。
  • 把 pi.live 当内存变量。它是已提交的文档；"实时"是高频小提交的观感，不是绕过存储。
  • 自定义条目 kinds 用 pi. 前缀。保留前缀，会被拒。
  • 以为 reset/压缩删除历史。它们只移动 head；旧条目仍在存储里，entries() 翻得到。
  • 在 commit 回调里调 Session 的读方法。回调持有提交线，直读 Session 可能排队死锁；回调里只准用 tx（第 6 章展开）。
