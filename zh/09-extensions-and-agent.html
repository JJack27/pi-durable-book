扩展（Extension）、注册表（Registry）与 Agent 配置

前面八章的零件 —— 工具、提示词段落、钩子、任务 —— 都靠扩展打包分发。 本章讲清：扩展是什么、注册表怎么装、会话怎么按名字选用（以及为什么存名字不存对象）、 system prompt 怎么拼、hooks 怎么拦截内置任务、以及热重载的边界在哪里。

学习目标
  • 能写出带 tools / sections / hooks / wraps 的扩展并装进注册表
  • 能解释「注册表不落盘、会话存名字」的设计，以及卸载-重装的后果
  • 能用 section() 写提示词段落，并说明位置化 pi.system 条目为何能保温 prompt 缓存
  • 能用 configure() 的数组/对象/null 三种形式精确表达 agent 变更
  • 能给三类内置任务挂钩子，并说出钩子抛错的后果
  • 能描述热重载规则：已在跑的调用用旧代码，下一个相位/请求用新代码

9.1 扩展：命名的能力包

import { defineExtension, defineTool, hook, section, ToolTask } from "@earendil-works/pi-durable";

const Coding = defineExtension({
	name: "coding",                       // 唯一身份：注册与选择都靠它
	tools: [/* ToolRegistration ... */],   // 提供工具
	sections: [                            // 提示词段落（按序渲染）
		section("preamble", () => "You are a concise coding assistant.", { tag: false }),
	],
	hooks: [                               // 拦截内置任务
		hook(ToolTask, { beforeTool: (call) => isDangerous(call) ? { block: "Needs approval" } : undefined }),
	],
	wraps: [/* 装饰别人同名工具/同名段落 */],
	tasks: [/* AnyTask ... */],            // 提供任务定义（按名解析，与选择无关）
});

const registry = createRegistry();
registry.install(CodingTools);   // 内置编码工具扩展
registry.install(Coding);

一条容易被忽略的规则：注册表里什么都不落盘，会话的 pi.agent 里存的是扩展名字。 于是名字比代码活得久 —— 卸载某扩展后，选了它的会话只是暂时拿不到它，等重新安装同名扩展又恢复。 默认每个会话按安装顺序选择全部已安装扩展；同名工具后者覆盖前者（装得晚的赢）。

9.2 注册表：装、卸、热替换

  • registry.install(ext) — 新名字追加；同名原地替换（一步完成，无中间态）。这就是热重载的实现机制。
  • registry.uninstall(ext) — 按 ext.name 移除已装的（不管传进来的对象是不是当年那个）。再装同名的会排到后面。
  • Harness 每次用时从 registry.snapshot() 拿不可变快照 —— 一个相位/一次请求内代码固定，快照之间可以变。注册表变化会同步唤醒调度器重新考虑被 blocked 的任务。

热重载边界（README Reload 一节）：已经开始的工作带着它启动时的代码跑完 —— 执行中的工具调用在旧实现下结束；每个任务相位开始时解析一次钩子与 agent。下一个相位、下一次请求、下一个调用用新代码。重启进程后要重新 install 一遍；某扩展 tasks 的 pending 任务等它装回来才恢复。

9.3 系统提示词：段落拼装与缓存友好

每次请求前，所选扩展的 sections 按序渲染，会话自己的 instructions 最后作为段落 instructions 渲染。段落签名：

section("cwd", (input) => input.env?.cwd);
// input: { conversationId, agent, env, shown, read }
// 返回 undefined 则省略该段；默认以 <cwd>...</cwd> 包裹（tag: false 关闭）

位置化的 pi.system 条目：sections 与工具集的变化被存成转录里的系统条目， 请求时只重发变化的部分。这是刻意讨好提供商的 prompt 缓存：前缀不变，缓存命中。 推论：一个每次返回不同内容的段落（比如当前时间）会击穿缓存 —— 把这类信息放进 instructions 或让它稳定，是使用者的责任。

9.4 pi.agent 与 configure()：会话跑什么的唯一事实

每个会话把「跑什么」存在 pi.agent（src/harness/agent.ts:43）。未设置的字段跟随宿主（settings 的默认选择）。configure(change) 用一个 commit 改它，三种形式各有语义：

await root.configure({
	model: { provider: "openai", modelId: "gpt-6-sol" },   // 给定字段：整体替换
	thinkingLevel: "high",
	extensions: { remove: [Coding] },   // 对象：编辑宿主默认选择（add / remove）
	tools: [readTool, bashTool],        // 数组：精确启用这些（按序）
	modelTools: [readTool],             // 缩窄给模型的名单（第 8 章）
	instructions: "Only read; never edit files.",
	cwd: "/work/repo",
}, context);
await root.configure({ tools: null }, context);            // null：清回宿主默认
const agent = await root.agent(context);                    // 解析结果（含 tools/callable/deferred）
  • 数组 = 「精确就是这些，按此顺序」；对象 = 「在默认之上增删」；null = 「清空，回到默认」。三个动词三种形状，记牢少踩坑。
  • 请求级固定：一次请求的模型、prompt、提供的工具在它准备时就固定了，configure 从下一次请求生效。
  • 继承：任务拥有的子会话从 owner 会话复制 agent 起步；fork 拿父会话在分叉条目时的 agent。
  • 扩展与工具都按对象传入、按名字存储 —— 与注册表同一套哲学。

9.5 Hooks：拦截内置任务

钩子按任务种类挂（hook(Task, handlers)，按定义名匹配），只在选择其扩展的会话生效：

  • 工具钩子（ToolHooks，types.ts:792-806）： beforeTool(call, api, ctx) — 阻止（{ block: "理由" }，首个阻止获胜）或改写参数（{ arguments: {...} }）；抛异常 = 阻止。 afterTool(call, result, api, ctx) — 替换结果（比如脱敏 —— 注意声明了 schema 的工具要连 structuredOutput 一起脱）。 嵌套调用的 call.parent 标记了它来自另一个工具。
  • 生成钩子（GenerationHooks，types.ts:771-784）： beforeRequest（换掉本次请求的消息）、afterResponse（每个终态 provider 消息）、 onYield（对最终回答说「继续干」：{ continue: UserInput }）、afterTools（一轮工具全部终态后）。
  • 压缩钩子（CompactionHooks，types.ts:809-826）： beforeCompact — 拒绝（{ decline: true }）或自带摘要（{ summary }），第 10 章配合压缩阈值使用。

HookApi 给钩子的能力（types.ts:758-766）：文档读、taskId / conversationId、models、以及与任务共享的 memo。钩子抛错只废自己：被上报（onReport）后跳过，beforeTool 抛错视为阻止 —— 内置工作不因扩展bug而停摆。

9.6 wrapTool / wrapSection：装饰赢家

const Timing = defineExtension({
	name: "timing",
	wraps: [wrapTool(bashTool, (bash) => ({
		...bash,
		execute: (args, api, ctx) => timed(() => bash.execute(args, api, ctx)),
	}))],
});

包装器作用于「同名的最终赢家」—— 先被覆盖再被包装，顺序不乱。包装器必须是纯函数（每次重新应用，不能带跨调用状态）。

9.7 本章回顾

  • 扩展 = name + tools + sections + hooks + wraps + tasks 的命名包；注册表可热变，快照保稳定。
  • 存储只存名字：卸载是「暂时消失」，重装即恢复；同名工具后装覆盖，包装器装饰赢家。
  • 提示词 = 扩展段落按序 + instructions 殿后；变化存成位置化 pi.system 条目，只重发送变化部分以保温缓存。
  • configure 三形式：数组（精确）、对象（增删）、null（清空）；请求准备时固化，下请求生效。
  • 钩子三类，全部「首个决定获胜、抛错只废自己」；HookApi 带 memo 与文档读。
  • 热重载边界：跑着的用旧代码跑完；重启后需要重新 install。
常见坑
  • 期待 configure 立刻改变进行中的请求 —— 请求准备时已固定，下个请求才轮到你。
  • 段落里渲染当前时间 —— 每次都变，prompt 缓存全穿。
  • afterTool 只脱敏 output 忘了 structuredOutput —— 程序侧拿到原文。
  • 以为钩子抛错会中止 run —— 只废该钩子，beforeTool 的抛错等价阻止该次调用。
  • 改了扩展实现却不重启进程也不 reinstall —— pending 的该扩展任务永远 blocked（定义名找不到新版本）。
  • 用 === 比较扩展/工具对象判断是否选择 —— 会话存的是名字，用 configure 的对象参数让框架按名处理。
