工具（Tools）与执行环境（Env）

模型只能"说话"，改变世界靠工具。本章讲透：怎么定义一个工具、它的三通道结果、 崩溃后的重放（replay）策略、谁能调用谁（callers）、工具套工具的嵌套调用（executeTool）、 以及所有工具副作用都流经的 ExecutionEnv —— 内置 read / write / edit / bash 就是活教材。

学习目标
  • 能用 defineTool 写出带 TypeBox 参数与结构化输出的工具
  • 能说清结果三通道 output / structuredOutput / details 各自给谁看
  • 能判断一个工具该标 replay: safe 还是默认 unsafe，以及崩溃后各自发生什么
  • 能用 callers / deferred / modelTools 控制模型与程序各自能看到、调用哪些工具
  • 能用 api.executeTool() 写工具套工具，并解释嵌套调用的 key 重挂机制
  • 能解释 ExecutionEnv 的作用与内置四个编码工具如何通过它接触世界

8.1 defineTool：一个工具的全貌

import { Type } from "@earendil-works/pi-ai";
import { defineTool } from "@earendil-works/pi-durable"; // src/harness/define.ts:13

const lines = defineTool({
	name: "lines",
	description: "统计一个文件的行数",
	parameters: Type.Object({ path: Type.String() }),       // TypeBox schema
	structuredOutputSchema: Type.Object({ lines: Type.Number() }), // 可选：程序侧契约
	replay: "safe",                    // 可选：崩溃中断后允许重跑（默认 "unsafe"）
	// callers: ["model"],            // 可选：谁能调用，见 8.4
	execute: async (args, api, context) => {     // args 类型由 parameters 推出
		const text = await readText(api, args.path, context);
		const count = text.split("\n").length;
		return {
			output: [{ type: "text", text: `${count} lines` }],  // 给模型
			structuredOutput: { lines: count },                  // 给程序，会被 schema 校验
		};
	},
});
registry.install(defineExtension({ name: "count", tools: [lines] }));

要点（src/harness/types.ts:294-334 的 ToolRegistration）：

  • 参数先验证再执行：Harness 在调 execute() 之前用 schema 验证模型给的参数。prepareArguments 可在验证前修补模型的常见错误（比如把数组写成了 JSON 字符串），且必须是纯函数。
  • 声明了 structuredOutputSchema 就必须给结构化输出（错误结果可豁免），Harness 负责校验；没声明却给了会怎样？—— 不允许，没有 schema 的工具程序侧直接拿它的 bounded output。
  • 流式输出：api.output(chunk) 边跑边写运行输出，UI 在 pi.live 里实时看到；execute() 返回时若省略 output，累计的运行输出就是给模型的输出。长输出用 api.retainedOutput() 拿"保留的尾部"；outputLimits 控制字节/行数上限与保留头还是尾。
  • execute 抛异常 → 模型收到一条错误结果（工具任务本身 failed，但 run 不因此终止）。

8.2 结果三通道：一份结果，三种读者

补充两条：结果可带 usage（工具自己调模型的耗费，计入 pi.usage.tools）；可带 control —— { terminate: true }（当轮所有结果都要求时提前结束 run，不再多问一次模型）、{ handoff: "..." }（重置并交接，等价于工具版 reset）、{ addTools: [...] }（加载延迟工具，见 8.4）。api.diagnostic() 记录模型可见的备注（截断、溢出路径等），bash 的结构化输出是 { output, truncated, fullOutputPath?, exitCode }，非零退出码会给错误结果但值仍携带。

8.3 replay：崩溃之后，工具要不要再跑一遍

工具调用的意图先于执行被提交（又是三明治）。进程死在 execute 中间时：

  • 默认（unsafe）：不重跑。模型收到一条 interrupted 错误结果，附已提交的部分输出。理由：你没法证明副作用没做，重跑可能双花。
  • replay: "safe"：重跑整个 execute。适用于可证明幂等的工具（纯读、带外部去重键的写）。重放安全是你的声明，框架只负责据此调度。

推论：不可重放工具的嵌套调用与它建的子任务自动 abandonOnRestart（第 7 章）—— 反正没人会回来等它们。反之，replay-safe 的工具重跑时，它之前的嵌套调用按 key 重新挂接而非重发（8.5）。

8.4 callers / deferred / modelTools：谁能看到谁

  • callers（types.ts:318-323）：谁可调用 —— ["model"]（仅模型，如 codemode，防脚本启动脚本）、["tools"]（仅其他工具经 executeTool，如藏在代码模式后面的 MCP 工具，模型永远看不到）、默认两者皆可。
  • deferred: true：先不给模型，直到被加载。配 @earendil-works/pi-durable/tool-search 的 createToolSearchExtension()：模型用 tool_search 搜到后经 control.addTools 加载，记录进 modelTools。大工具集（整个 MCP 服务器）的标准做法。
  • modelTools（会话配置，第 9 章）：在已启用的工具里缩窄"提供给模型"的名单，但不影响工具间互相调用。

conversation.agent() 的解析结果直接体现这套过滤：tools（给模型的）、callable（程序可调的）、deferred（可加载的）三个列表。

8.5 嵌套调用：api.executeTool()

工具里调工具，每次嵌套调用都是独立的 pi.tool 任务，归调用者所有：

const testsPass = defineTool({
	name: "tests_pass",
	description: "跑测试并回答是否通过",
	parameters: Type.Object({}),
	execute: async (_args, api, context) => {
		const run = await api.executeTool("bash", { command: "npm test" }, context, { progress: false });
		// bash 声明了 schema：非零退出也有 structuredOutput
		const exitCode = (run.structuredOutput as { exitCode: number } | undefined)?.exitCode;
		return { output: [{ type: "text", text: exitCode === 0 ? "passed" : "failed" }] };
	},
});

嵌套调用的规则几乎每条都有用（types.ts:256-287 的长注释）：

  • 调用方拿到 taskId / structuredOutput / details / diagnostics / usage / isError —— 拿不到给模型的 output。被阻塞、无效、失败、中止的嵌套调用返回 isError 结果而不是 reject。
  • key 重挂：每个嵌套调用有 key（默认是它在本次调用里的序号 1、2、…，也可显式传）。replay-safe 的调用者崩溃重跑时，按相同顺序（或相同 key）发出的调用会接回既有任务（已完成的拿结果，在跑的等它），不重复执行。注意被崩溃打断在结果提交前的那个嵌套调用，按它自己的 replay 策略处理 —— 所以这不是精确一次执行。
  • progress: false：不为嵌套调用提交运行输出，只提交状态 —— 省写放大，代价是中断后结果里没有部分输出。
  • 调用者返回前，它留下的仍在跑的嵌套调用会被中止；嵌套结果不长期保存（调用者结算后即清，任务记录里只留小回执）。
  • 嵌套调用的 usage 已计在自己工具名下，结果里再转交会算两遍。
  • 深度无上限，默认 callers 的工具甚至能递归调自己 —— 需要限制就用 callers。

8.6 ExecutionEnv：工具触碰世界的唯一通道

工具不直接 fs.readFile、不直接 child_process。 一切文件与进程访问都走 api.env —— 一个由 HarnessOptions.env 按调用现建的执行环境对象。这个设计买来三样东西：

  • 沙箱可换：默认 NodeExecutionEnv（本机文件系统 + 无 shell 的 argv 执行）；你可以每会话一个容器、每会话一个远程目录 —— 只需一个函数（src/env/index.ts 的 ExecutionEnv 接口：读文件、读目录、exec、cleanup、可选 listFiles，id 用于按路径串行化写）。
  • 审查有钩子：beforeTool 钩子看到的是即将进环境的参数；env 抛错会成为该次调用的错误结果。
  • 宿主复用：宿主自己也能用 env 展示项目文件：openBinaryReader()（字节区间读）、openDirReader()（分页目录）、exec(["git","status"], { onOutput }, context)（argv 数组、无 shell、标注输出流）。
import { NodeExecutionEnv } from "@earendil-works/pi-durable/env/node";

const harness = await Harness.open(storage, {
	models, registry,
	env: ({ cwd }) => new NodeExecutionEnv({ cwd: cwd ?? process.cwd() }),
}, context);

8.7 内置编码工具：read / write / edit / bash

@earendil-works/pi-durable/tools 提供（src/tools/index.ts）：

  • createReadTool() / createWriteTool() / createEditTool() / createBashTool() —— 单件工厂（bash 支持 commandPrefix，如自动激活 venv）；
  • createCodingTools(options) —— 打包四件的扩展；CodingTools 是默认实例；
  • 同名后装覆盖先装（扩展顺序决定胜负），wrapTool 装饰赢家（第 9 章）；
  • read 读图片文件返回图像块：尺寸/大小限制按模型的 inputLimits.images.resize（默认 2000×2000、4.5MB base64）。装上 createNodePhotonImages()（/images/node，WebAssembly 的 Photon，工作线程里解码、30 秒闲置退出）后才会解码/旋转/缩放；不装则 PNG/JPEG/GIF/WebP 原样直传、超限拒绝。内存紧张的宿主（Cloudflare）别装。

8.8 本章回顾

  • defineTool：TypeBox 参数先验证后执行；三通道结果；流式 api.output；异常变错误结果。
  • replay：unsafe（默认，中断后模型拿 interrupted 错误）vs safe（声明幂等，重跑）。
  • callers 分模型/程序两侧；deferred + tool_search 按需加载；modelTools 缩窄模型视野。
  • executeTool：嵌套即子任务，key 重挂保证 replay-safe 调用者不重复副作用；程序拿 structuredOutput 不拿 output。
  • ExecutionEnv 是工具触碰世界的唯一通道，按调用现建、可沙箱可远程。
  • 内置 read/write/edit/bash + CodingTools；图片处理按需装 Photon。
常见坑
  • 给不安全的工具标 replay: safe —— 双花、重复发邮件都是这么来的；先有幂等证据再标。
  • 声明了 structuredOutputSchema 却在错误路径上不给值 —— 程序侧拿到 invalid_structured_output 错误结果。
  • 把嵌套调用的 usage 原样转交到自己的结果里 —— 计费翻倍。
  • 以为 executeTool 拿到的 structuredOutput 永远存在 —— 无 schema 工具给的是 bounded output，Harness 自写的错误结果（blocked/invalid/interrupted/aborted）根本不带。
  • 没配 HarnessOptions.env 就用内置工具 —— 工具以错误结果失败，这行报错是配置提示。
  • expecting 嵌套调用按 executionMode 排队 —— 嵌套调用立刻开跑，并发由你 await 什么决定。
