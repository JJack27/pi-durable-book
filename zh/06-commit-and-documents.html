Commit 深挖：Tx 事务面与 Document 文档系统

commit 是整个包的地基。本章回答四个问题：代码里到底有哪几个 commit 入口； 事务对象 Tx 上能做什么、不能做什么；为什么"回调里只准用 tx 读"； 以及文档（Document）这套类型化 JSON 状态怎么定义、怎么读、怎么在 fork 时表现。

学习目标
  • 能列出四个 commit 入口及其适用场景（宿主 / 会话 / 任务 / 工具）
  • 能说出 Tx 的三类操作（读、写、文档）并各举两个方法
  • 能解释 ReadAfterWrite 错误与"回调里禁止 Session 读"的原因
  • 能用 defineDoc 写出带版本迁移的文档，并选对 scope / history / fork 语义
  • 能区分 snapshot / snapshotAsOf / documentState / watchDoc 四种读法

6.1 四个 commit 入口

同一台原子提交机器，有四个方向盘：

  • harness.commit(cb, context)（Session 继承，src/types.ts:955）— 宿主的裸提交线，不绑定会话。创建不归属任何会话的会话级文档、做全局记账时用。
  • conversation.commit(cb, context)（src/harness/harness.ts:124-126）— 最常用。与裸提交的差别只有一处：其 tx.createTask() 默认归属该会话。
  • runtime.commit(cb, context)（任务里，src/types.ts:197-203）— 任务专用：在 Session 线上提交，回调的返回值若是一个任务状态就同时替换本任务的状态（推进检查点 / 声明终态都在这一步）。第 7 章的主角。
  • api.commit(cb, context)（工具里，src/harness/types.ts:238）— 工具执行中写条目/文档/建子任务用。同样是原子的。

四个入口汇进同一条串行化的变更线：两个并发的 commit 不会交错，先到先得。这就是 spec 所说的 mutation line —— 所有原子性的根源。

6.2 Tx 表面：事务回调里能做什么

Tx 接口（src/types.ts:791-886）按用途分三组：

  • 读（都是存储一致读）： conversation(id) / entry(id)（含类型化重载）/ task(id)； 四个 scan：scanConversations、scanEntries、scanTasks、 latestHeadMarker(conversationId)；submissionByRequest(conversationId, requestId)。
  • 写（随本 commit 落盘）： createConversation({ ownership }) / forkConversation(parentId, at, { ownership })； appendEntry(conversationId, draft)（或带类型令牌版 appendEntry(Token, conversationId, typedDraft)）； createTask(task, input, options)； createSubmission(create) / settleSubmission(id, settlement) / placeSubmission(id, entryId)（后两个主要给实现接纳逻辑的内置代码用）。
  • 文档：六个重载的 doc(token, ...ownerId, ...key, seed) 拿到可变 Draft 改完即提交； retireDoc(token, ...) 退役一个文档。

一个组合小例（会话级配置 + 条目 + 任务一锅端）：

await root.commit(async (tx) => {
	const note = await tx.appendEntry(root.id, {
		kind: "app.note",
		data: { text: "切换前先记录" },
	});
	const todos = await tx.doc(Todos, root.id);   // Draft：直接改
	todos.items.push(`note-${note.id}`);
	if (todos.items.length > 3) {
		await tx.createTask(Cleanup, { since: note.id }, { ownership: { kind: "conversation" } });
	}
	return todos.items.length;                     // commit 的返回值
}, context);

6.3 三条事务规则

  1. 回调抛异常 = 整个提交回滚。 不是"写到哪算哪"—— storage.commit() 根本不会被调用， 所有暂存写入作废。你的错误原样传播给 commit 的调用者。
  2. 写后读表 = ReadAfterWrite。 事务里一旦写了表（建会话、建任务这类"表记录"），再用 tx 读表会抛 ReadAfterWrite（导出自 src/errors.ts）。 这与实现方式有关：tx 的读走的是进入事务时的快照语义，写入还没落盘，读回来只会自欺欺人， 所以直接禁止。文档读写不受影响 —— tx.doc() 之后继续读写文档没问题。 ConversationInit 的文档注释（src/harness/types.ts:464-468）就明说了： 建会话是表写，init 里读表会抛 ReadAfterWrite，文档访问照常。
  3. 回调里只准用 tx 读。 Session 自己的读方法（snapshot()、getTask() 等）会排队在 你这回调占着的提交线后面 —— 永远排不到，死锁。 四个 commit 入口的文档注释都重复这句警告（如 src/types.ts:953）。 需要读，用 tx；实在要 Session 读，先结束这个 commit。

6.4 Document：定义你自己的持久状态

文档 = 会话/任务旁边的一块类型化 JSON 状态，只能在 commit 里改。定义用 defineDoc()（src/documents.ts:39）：

import { defineDoc } from "@earendil-works/pi-durable";

const Todos = defineDoc<{ items: string[] }>({
	kind: "app.todos",      // 持久化种类名（协议的一部分，别改）
	version: 1,             // 存储值形状的版本号（正整数）
	scope: "conversation",  // 归属：session / conversation / task
	history: "latest",      // conversation 专属：latest 只留当前值 / rewindable 可按历史读
	fork: "initial",        // conversation 专属：fork 时继承 initial / current / asOf
	initial: () => ({ items: [] }),
	migrate: (value, fromVersion) => ({ ...value, items: value.items ?? [] }), // 可选
});

// 写（只能进 commit）：
await root.commit((tx) => {
	(await tx.doc(Todos, root.id)).items.push("写文档");
}, context);

// 读快照：
console.log(await harness.snapshot(Todos, root.id, context));

三个维度决定一个文档的行为：

  • scope — session（全局一份）、conversation（每会话一份）、task（每任务一份）。还有家族版 defineDocFamily：同一 scope 下按键（key）开多份，initial(seed) 只在成员缺席时运行。
  • history（仅 conversation）— latest 只保留当前值，省空间；rewindable 保留历史，可用 snapshotAsOf(token, conversationId, entryId) 读"某条历史条目时点"的值 —— 分叉回放、审计都需要它。
  • fork（仅 conversation）— 分叉时新会话拿到什么：initial（全新初始值）、current（父会话当前值）、asOf（分叉点时值，要求 rewindable）。

写入细节：你对 Draft 的修改被 diff 成增量（delta ops）存储，存储层偶尔按 checkpointWhen 的判断写完整基线（base），崩溃只可能丢"还没提交的"， 已提交的增量链永远自洽。版本升级：调高 version 并提供 migrate(value, fromVersion)，旧值在读取时被迁移。忘了写 migrate 而存着旧版本， 类型化访问会抛错提醒你。

6.5 四种读法

  • harness.snapshot(token, ...) — 一次性读当前值（Readonly<T> | undefined）。请求-响应式代码用。
  • harness.snapshotAsOf(token, conversationId, at, context) — 读 rewindable 文档在历史某条目时点的值。
  • harness.documentState(token, ...) — 拿一个可订阅的状态对象（Chord 的 AttachedReplicatedState）：后续提交自动推进，UI 直接订阅。
  • harness.watchDoc(token, ...) — 拿逐帧的精确观察（带增量 ops 的 watch handle），做同步器/远端镜像时用。

选择口径：偶尔读用 snapshot；界面常驻用 documentState；要把变更精确传给另一个进程/客户端用 watchDoc。第 10 章的会话级 viewState / watch 是这些原语在"整份会话视图"上的组合。

6.6 本章回顾

  • 四个 commit 入口共用一条串行提交线；Conversation.commit 的 tx.createTask 默认归属该会话。
  • Tx 三组操作：读（scan/单查）、写（建会话/条目/任务/提交）、文档（doc/retireDoc）。
  • 三条规则：回调抛错全回滚；表写后读表抛 ReadAfterWrite（文档不受限）；回调里禁止 Session 读（会死锁），只准用 tx。
  • 文档三维度：scope（session/conversation/task + family）、history（latest/rewindable）、fork（initial/current/asOf）；版本靠 migrate 升级。
  • 读法四件套：snapshot / snapshotAsOf / documentState / watchDoc。
常见坑
  • 在 init / conversationCreated 回调里 tx.scanConversations(...) —— 建会话是表写，随后读表抛 ReadAfterWrite；要读文档或改用创建返回的 record。
  • commit 回调里图方便调 harness.snapshot —— 死锁。用 tx。
  • 改了文档形状却不动 version —— 旧数据按旧形状读出新代码，炸在远方。version + migrate 成对出现。
  • 以为 Draft 是拷贝 —— 它就是本次事务里的文档本体，改完即提交，别缓存它跨事务使用。
  • 用 latest 文档却想读历史值 —— 需要 rewindable + snapshotAsOf，latest 根本没存历史。
