第一个程序：Quick Start 逐行精读

本章把 README 的 Quick Start 十几行代码逐行拆开。读完你能独立写出"问一个问题、拿到回答、 打印出来"的完整程序，并且明白每个调用在存储里留下了什么。

学习目标
  • 能默写 Quick Start 的骨架：open → root → submit → wait → commit → close
  • 能说出 Harness.open() 对 registry 做的校验，以及忘了 createRegistry() 会怎样
  • 能解释最后一行 commit 里 tx.entry(AssistantEntry, ...) 为什么是"读"而不是"写"
  • 知道怎么在仓库里跑现成示例（faux provider 与真实 OpenAI 的差别）

3.1 完整代码

以下与 packages/durable/README.md:48-69 一致（注释为本书所加）：

import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { openaiProvider } from "@earendil-works/pi-ai/providers/openai";
import { AssistantEntry, createRegistry, Harness, MemoryStorage } from "@earendil-works/pi-durable";

const context = BACKGROUND_CONTEXT;                      // ① 永不取消的上下文

const models = createModels();
models.setProvider(openaiProvider());                    // ② 模型目录：读 OPENAI_API_KEY

const harness = await Harness.open(                      // ③ 打开一个 Harness
	new MemoryStorage(),                                  //    内存存储：进程结束即消失
	{ models, registry: createRegistry() },               //    模型目录 + 扩展注册表
	context,
);
const root = await harness.root(context, {               // ④ 根会话（首次调用时创建）
	agent: { model: { provider: "openai", modelId: "gpt-6-sol" } },
});

const submission = await root.submit(                    // ⑤ 持久接纳一条用户输入
	{ type: "input", content: "What is the capital of France?" },
	context,
);
const settled = await submission.wait(context);          // ⑥ 等它被回答
if (settled.status === "done" && settled.type === "input") {
	const answer = await root.commit(                    // ⑦ 用一次事务读取答案条目
		(tx) => tx.entry(AssistantEntry, settled.answer),
		context,
	);
	console.log(answer?.model?.[0]);                     //    打印 AssistantMessage
}
await harness.close(context);                            // ⑧ 收摊

3.2 逐行精读

① BACKGROUND_CONTEXT —— Chord 的取消上下文，永不触发取消。 pi-durable 里每个异步 API 的最后一个参数都是 Context。真实产品里你会传能取消的 context（比如绑定到 HTTP 请求的生命周期）；这里为了示例从简。

② 模型目录 —— pi-durable 不自己认识 OpenAI。createModels() 建 pi-ai 的目录对象，setProvider(openaiProvider()) 注册 OpenAI 提供商（凭据从 OPENAI_API_KEY 环境变量读）。这个对象之后交给 Harness，所有模型请求（生成、压缩摘要） 都经它发出。

③ Harness.open(storage, options, context) —— 打开存储并启动机械。 实现在 src/harness/harness.ts:460-485，有一个值得记住的启动校验 （harness.ts:468-473）：它会检查注册表里内置任务（pi.generation、 pi.tool、pi.compaction）是否齐备，缺了就抛 "Registry lacks built-in tasks …; create it with createRegistry()"。 也就是说 registry 必须用 createRegistry() 建 —— 它预装了内置任务。 MemoryStorage 让一切留在内存：学习用最合适，第 4 章换成 SQLite 就能跨进程。

④ harness.root(context, { agent }) —— 拿根会话。 存储里还没有根会话时，这一次调用在一个 commit 里创建它并应用 agent 变更（src/harness/harness.ts:356-373 的 #create）：写入空的 pi.live / pi.inbox / pi.usage、新的 pi.provider 身份、以及含模型选择的 pi.agent。再次调用直接返回已有的根（ID 恒为 1）。

⑤ root.submit({ type: "input", content }, context) —— 持久接纳输入。submit() 返回一个可等待的 Submission 对象。 "接纳"（admit）意味着输入已被原子提交进存储（一条 pi.user 条目 + 一条提交记录），此刻哪怕进程死掉，重开后它仍在。接下来内置的 generation 任务接手：调模型、 把回答写为 pi.assistant 条目。

⑥ submission.wait(context) —— 等待落定。结果 （SettledSubmissionRecord，src/harness/types.ts:81）只有两种终态： done（有 answer: EntryId）或 unanswered（带 reason）。 注意 wait 只是等待的取消侧 —— 取消 context 只放弃这次等待，工作照常进行。

⑦ 最后那次 commit —— 一个容易看走眼的点。

const answer = await root.commit((tx) => tx.entry(AssistantEntry, settled.answer), context);

这里的 tx.entry(...) 不是写入，是读取。Tx 接口上 entry 有两个重载（src/types.ts:793-795）：按 ID 读原始条目； 或者带一个类型令牌读 —— tx.entry(AssistantEntry, id) 返回按 pi.assistant 类型收窄的 TypedEntry，类型不对则 undefined。 settled.answer 只是答案条目的 ID，这一步在事务里把它读出来； answer?.model?.[0] 就是那条 AssistantMessage。 顺带学到 commit 的另一个性质：回调的返回值原样成为 commit() 的返回值， 所以 commit 不只能写，也能做事务性的一致读。

⑧ harness.close(context) —— 关闭会先封住新提交、等正在跑的 任务代码返回、再关存储。被中断的工作保持 pending，下次打开存储再续（第 4 章）。

3.3 跑仓库里的现成示例

packages/durable/test/examples/ 下有 20 多个可运行示例，从 00 到 31 编号， 由浅入深。在 packages/durable 目录下这样跑（README 的方法，仓库内直接跑 TypeScript 源码）： 

cd packages/durable
node --conditions=source --experimental-strip-types test/examples/14-chat.ts
  • 调 OpenAI 的示例需要 OPENAI_API_KEY；其余大多用 faux provider（假模型）跑，不需要任何 key。
  • 值得按顺序看：14-chat（一问一答）、20-inbox（忙时排队）、24-child-tasks（子任务与重启）、26-coding-agent（接近真实产品形态）。
  • 19-json.ts 展示完整的事件流输出 —— 第 10 章讲 watchEvents 时会回头引用它。

另一个提醒：仓库测试要求 Node ≥ 22.19.0（package.json:140-143 的 engines 字段）， --experimental-strip-types 直接执行 .ts 源文件依赖较新的 Node。

3.4 本章回顾

  • 骨架六步：open → root → submit → wait → commit(读答案) → close。
  • registry 必须用 createRegistry() 创建，否则 Harness.open() 校验失败。
  • root() 首次调用在一个 commit 里创建根会话并写入五个 pi.* 文档。
  • submit 即接纳：输入立刻持久；回答由内置 generation 任务写入。
  • tx.entry(Token, id) 是类型化读取重载；commit 回调的返回值即 commit 的返回值。
  • 示例都在 test/examples/，faux provider 不需要 key。
常见坑
  • 自己 new 一个空 registry 传给 open → 启动即抛 "Registry lacks built-in tasks"。
  • 以为 root() 每次都新建会话 —— 只有第一次创建，之后返回同一个（ID=1）。
  • 把 settled.answer 当成消息文本 —— 它是 EntryId，要再读一次条目。
  • 忘记 close() —— 测试进程会挂着不退（调度器还活着）。
  • 用 MemoryStorage 却期待跨进程续跑 —— 它什么都不持久化，第 4 章换后端。
