提交队列、观看、压缩与错误模型

最后四块运行时行为：会话忙的时候新消息去哪（inbox 与三种 whenBusy）； UI 怎么零遗漏地看（viewState / watch / watchEvents）；上下文太长怎么办（compaction 的手动与自动）； 以及出错时爆炸半径的精确规则。读完本章，你具备通读 spec.md 的全部前置知识。

学习目标
  • 能区分 steer / followUp / reject 三种 whenBusy 行为与纯 write 的特殊待遇
  • 能按场景选 viewState / watch / watchEvents 三种观察方式
  • 能配置自动压缩阈值（reserveTokens / keepRecentTokens / backgroundTokens）并解释溢出重试
  • 能复述错误三规则，判断任一错误的爆炸半径

10.1 会话忙时：inbox 与三种 whenBusy

会话在 run 进行中即「忙」。此刻提交一条 input，默认排队进 pi.inbox；你也可以改行为：

await root.submit({ type: "input", content: "顺便跑下测试" }, context);                    // 默认：followUp
await root.submit({ type: "input", content: "用 pnpm 别用 npm", whenBusy: "steer" }, context); // 插队转向
await root.submit({ type: "input", content: "只在不忙时发", whenBusy: "reject" }, context);    // 抛 ConversationBusy
await root.submit({ type: "write", entry: { kind: "app.note", data: {...} } }, context);      // 被动写入
  • steer（转向）：排在当前工具轮之后，汇入正在跑的 run —— 模型下一轮就看见。
  • followUp（追问，默认）：等 run 回答完再放置，开启下一个 run。
  • reject：直接抛 ConversationBusy，什么都不写。
  • write 的特殊待遇：只带 kind+data 的纯展示性写入立刻追加、永不排队 —— 它不影响模型所见，聊天界面发一条就显示一条。带 model/head/edits 的写入则按 steer 的规矩等边界。
  • 排队的 input 可撤回：submission.abort(context)（已放置的返回 already_placed）。
  • settings 的 steeringMode / followUpMode（"all" | "one-at-a-time"）决定一个边界放一批还是放一条。
  • run 失败时，排队项留在 inbox，等下一次输入或排队写入按最旧优先放置。

另一个实用细节：input 可以指定 entry 决定它在转录里长什么样（比如 chat.mention 带作者信息），模型看到的仍是 content 的用户消息 —— 自定义 kind 不得以 pi. 开头。

10.2 观看会话：三种方式

  • viewState() — 会话的结构化视图（ConversationView： conversation / entries / docs，见 src/harness/view.ts:19-27） 包成可订阅的只读状态：view.subscribe(render); ...; view.dispose()。 本进程 UI 的默认选择。
  • watch() — 同一份视图的精确帧流：每次提交一帧， 带这一帧的 Chord 增量 ops —— 适合转发给远端客户端原样应用。慢消费者最多积压 100 帧， 之后合并成一帧整视图；晚加入/重连的客户端从当前视图开始，不重放历史。
  • watchEvents(harness, conversationId, context)（实验性）— 面向习惯 coding-agent 事件流（message_start、tool_execution_start…）的消费者： 先给一个 snapshot，之后每个提交一批带增量的事件。test/examples/19-json.ts 有完整输出。

「实时感」的来源是进度提交节奏（settings.progress，默认各 100ms）：半截回答与工具输出至多每 100ms 提交一次 —— 崩溃至多丢这一窗。远端存储可调大间隔省写。

10.3 压缩：把旧上下文叠进一条摘要

// 手动：立即安排压缩任务（会话继续工作，摘要就绪后在下一个边界放置）
const id = await root.compact("保留失败测试的名字", context);

// 自动：settings.compaction
compaction: {
	enabled: true,            // 阈值/溢出压缩开关（手动 compact 永远可用）
	reserveTokens: 16384,     // 高于 contextWindow - reserveTokens：下一次请求阻塞等压缩
	keepRecentTokens: 20000,  // 摘要大致保留多长的近期原文
	backgroundTokens: 32768,  // 距阻塞阈值还差这么多时：后台先行压缩（0 关闭）
	modelOverrides: { "local/small-32k": { reserveTokens: 4096, ... } }, // 按模型覆盖
}
  • 摘要写入 pi.compaction 条目并立起新 head；老条目照例留在存储。
  • 溢出自救：提供商因上下文超长拒绝请求时，生成任务压缩后重试一次。
  • 多个压缩在飞时，唯一生效的是切得最深的那个；被超越的按 stale 落定（unanswered，reason "stale"）。
  • 阻塞阈值上的压缩失败 → 等它的生成也失败（unanswered，model_error，detail Compaction failed: ...）；没东西可压或被钩子拒绝则放行请求。
  • beforeCompact 钩子可拒绝（decline）或自带摘要；运行中的压缩列在 pi.live.compactions，最近失败留在 pi.live.compactionFailure。
  • reset(handoff) 是更狠的手段：不摘要，直接另起新上下文，可选留一句交接说明。工具侧等价物是 control.handoff。

10.4 错误模型：三条规则定爆炸半径

README Errors 一节的原文骨架（README.md:719-733）：

  1. 存储错误终结 Harness。撞上它的那个调用带着原始错误 reject；此后一切调用与所有挂起的 wait 以 SessionFailed（cause 是那个错误）reject；watch 与事件流以 session_failed 结束；运行中任务收到中止信号；onReport 收到一次错误；Harness 自行关闭。不重试（瞬时错误应在你自定义存储里自己重试）。恢复 = 重开存储：提交是原子的，存储一致，同 requestId 能找回已接纳的提交。
  2. 无效读只废这次调用。StorageRequestError：坏游标、未知会话、读了文档不保留的历史；被取消的读同理。豁免只覆盖读 —— commit() 或 mintId() 抛 StorageRequestError 照样按规则一处理。
  3. 你的代码只废自己的单元。任务相位抛错 → 该任务 faulted；工具抛错 → 错误结果；钩子抛错 → 上报后跳过（beforeTool 视为阻止）；commit 回调抛错 → 回滚该提交。监听器抛错被上报，其余照跑。唯一例外：宿主 RegistryReader 的 snapshot() 抛错 —— 调度器没法干活，等同存储错误处理。

故障重启的标准写法：

harness.closed.then((end) => {
	if (end.reason === "failed") reopen(end.error);  // 重开存储、resume、同 requestId 重试
});

10.6 本章回顾（也是全书回顾）

  • 忙会话三选一：steer 插当前工具轮后、followUp 等下个 run、reject 抛 ConversationBusy；纯 write 立即追加不排队。
  • 观察三件套：viewState（本机 UI）、watch（精确帧转发远端）、watchEvents（事件流风格）；进度默认 100ms 一提交。
  • 压缩双通道：手动 compact 随时；自动三阈值（阻塞 reserve / 保留 keepRecent / 后台 background）+ modelOverrides；溢出压缩后重试一次；reset 是不摘要的另起炉灶。
  • 错误三规则：存储错废 Harness（不重试，重开恢复）、无效读只废本次、你的代码只废自己单元。
  • 全书主线一句话：一切先提交、后展示；任务带检查点；所有权树定级联 —— 这三条撑起了其余所有 API。
常见坑
  • 期待 reject 的提交留下点什么 —— 它什么都不写，异常就是全部信息。
  • 纯 write 带上了 model 字段还纳闷为什么不立刻显示 —— 带 model/head/edits 的写入要等边界，只有 kind+data 的纯展示写入立即追加。
  • 给 32k 小模型配全局 16k reserve —— 没剩多少可用了；用 modelOverrides 按模型分档。
  • watch 客户端断线重连后等重放 —— 没有；从当前整视图开始。
  • 存储报错后继续用旧 harness —— 已 SessionFailed，一切调用都拒绝；重开。
  • 以为 onReport 里抛错能引起注意 —— 它自己的异常被丢弃（它是错误的最后一站）。
